# Radical Cobblemon Trainers: what it supports for a repeatable-fight arena

**Question.** A "Heaven's Arena" tower in the Windward Deep pit — tiers climbing upward, a champion
holding each tier, a player challenges a champion for their place, endless fights, real money. Can that
be built on rctmod with datapack data and functions alone?

**Answered for:** rctmod **0.19.0-beta**, rctapi **0.16.1-beta**, Cobblemon **1.8.0+1.21.1**, Minecraft
1.21.1 Fabric — the server's runtime (`docs/STATE.md:13`). Note the base-pack snapshot is older
(rctmod 0.18.1-beta, rctapi 0.15.2-beta: `base-pack/inventory/mod_inventory.md:117-118`), and the
official documentation site is published only as **`latest`** with no version selector in the path
(`https://srcmc.gitlab.io/rct/docs/latest/`), so every doc claim below is "latest as of 2026-10-01" and
is *not* pinned to 0.19.0. Where our own jar reads and in-game observations disagree with the docs, the
jar wins and the disagreement is called out.

**The jars are not in this worktree.** `base-pack/cobbleverse/mods/*.jar` matched nothing
(gitignored, machine-local, and `.worktreeinclude` copied none of them), so nothing here is a fresh
bytecode read. The bytecode facts below are quoted from earlier reads recorded in the repo
(`tools/route_trainers.py`, `docs/STATE.md`, `experiments/EXP-020`, `experiments/EXP-027`) and are
labelled as such. Bash was also unavailable to this session (see "Refusals", last section).

---

## 0. The plain answer

**Yes — an endless-ladder arena can be built on rctmod with datapack data and functions alone, and the
hardest-looking requirement (endless rematches) is already rctmod's behaviour for the trainers we
place.** Nothing in the design below needs a mod we do not have. Three things are *not* free:

1. **"Who holds tier N" cannot be rctmod state.** An rctmod trainer is one shared entity with global
   NBT; `Cooldown` is entity NBT, so it cannot be held per player
   (`tools/route_trainers.py:366-370`). The per-player holder must live in **our** state, and three
   mechanisms already work in this repo: a **scoreboard objective**, an **advancement flag**
   (`cobblers:flag/*`, EXP-027), and the **MoLang quest fields** `route_trainers.py` already writes
   through `runmolang` + `q.player.data()` / `q.player.save_data()`
   (`tools/route_trainers.py:216`). A fourth, rctmod's own, is **`rctmod player get/set defeats
   <trainerId> <player> <value>`** — a per-player, op-settable, persistent counter (see §3). For a
   ladder, the quest-field or scoreboard route is preferable because it is ours and is already
   installed and proven.
2. **A tier champion's team cannot be generated by rctmod.** The team is a static array. See §2 — the
   ladder gets variety from *many authored trainer ids* plus a function choosing which to summon, or
   from our own generator emitting the JSON, not from a runtime pool.
3. **Only one player can visibly "hold" a tier.** One entity stands on the tier and every player sees
   the same one. A per-player champion identity would need per-player entities, which rctmod does not
   have (§3). Design the fiction so that the *tier's champion is fixed* and what is per-player is the
   player's own record of having taken it.

**So for an arena: repeatability is the default, not the feature to build.** The work is the opposite —
*holding a champion off* between legitimate challenges, which is the `Cooldown` merge we already do.

### ASSUMED

- That `maxTrainerDefeats: -1` would also give endless rematches on a **non-persistent** trainer (one
  from a `trainer_spawner`). Only inferred from the doc sentence; our placed trainers bypass the check
  entirely so we have never exercised the `-1` path. A tower that spawns its champions from
  `rctmod:trainer_spawner` blocks rather than `summon_persistent` is on the **documented** path, not
  the bypass, and should set `maxTrainerDefeats: -1` explicitly rather than rely on the bypass.
- That `battleCooldownTicks` and a merged `Cooldown` are the same counter. The docs describe one
  cooldown and one tag and our merge works; that they are one field is an inference.

### Disagreement inside the repo (a finding, not papered over)

`docs/mechanics/GYM_INTERIORS.md:178-189` says the cooldown is written "**only while every nearby
player has beaten it**", and lists the mixed-progress pair as the consequence. That is stale:
`tools/route_trainers.py:363-372` records the owner's 2026-09-29 change to fire the hold-off whenever
**any** nearby player has beaten the trainer, protecting the beaten player and leaving an unbeaten
partner to start the fight by interacting. The generator is the truth; the mechanics doc describes the
superseded line.

### VERIFIED

| Claim | Source |

| The same page documents **no** field for team generation, randomisation, level scaling to the player, or pool selection | docs `configuration/data_pack/trainers/`, read for exactly this question |
| rctapi 0.16's `TrainerModel` reads `name`, `ai`, `bag`, `team`, `battleTheme`; `battleRules` is rctmod's own key | jar read 2026-09-24, recorded `tools/route_trainers.py:34-38` |
| `battleFormat` must be written explicitly in any file that **overrides** an upstream trainer, because the override replaces upstream's whole file; all twelve of ours were silently dropping `GEN_9_SINGLES` until that was fixed | `tools/route_trainers.py:241-244` |
| Overriding is per-file with a three-tier fallback — `single/` beats `groups/` beats a default at the asset root ("defaults can only be overriden") | docs `configuration/fallback_data_system/` |
| Cobblemon 1.8.0 added `party_pools` ("defining groups of Pokémon for complex NPC party definitions"), `party_compositions` ("arranging parties on NPCs that rely on party pools"), a `composed_pool` **NPC party provider** type, and `moveset_builders` | Cobblemon wiki `1.8.0` changelog page |
| `moveset_builders` exists as a real loaded Cobblemon datapack directory in the installed 1.8.0 jar | `docs/research/notes/starter-selection.md:132` (directory list read from the jar) |
| The rctmod **Pack Builder** is a web tool that imports/exports pack assets and "will keep their identity" and "copy the properties" of imported trainers — an editor, not a generator | docs `tools/pack_builder/about/` |

**The decisive point:** `party_pools` / `party_compositions` / `composed_pool` are documented as **NPC
party providers**, i.e. they belong to Cobblemon's own `cobblemon:npc` entity and its party-provider
field. rctmod's trainers are `rctmod:trainer` entities with rctapi's `TrainerModel`, which reads a
literal `team` array. There is **no evidence of any path by which a Cobblemon party pool reaches an
rctmod trainer**, and rctapi's model has no field that could carry one.

### ASSUMED

- That a Cobblemon `cobblemon:npc` with a `composed_pool` provider therefore *is* a viable alternative
  engine for randomised arena teams. Plausible and the changelog supports the feature existing, but
  **the NPC party-provider schema was not obtainable**: `wiki.cobblemon.com/index.php/NPC` and
  `/NPCs` both returned HTTP 404 and search found no page quoting the provider type ids. Nothing about
  Cobblemon NPC battles (how a battle starts, whether it is repeatable, whether it has a cooldown, what
  is per player) is verified here. Treat "use Cobblemon NPCs for randomised teams" as an unexplored
  option, not a fallback we know works. (`docs/research/CASINO.md:258` already flags party pools as
  "named in CLAUDE.md but unexplored".)

### What a tier champion with a not-hand-authored team can actually be, today

1. **Generated at build time by our own tool.** This is the established pattern:
   `tools/route_trainers.py` already emits `data/rctmod/trainers/<id>.json` from our records, and
   `docs/world-building/NAVIGATION.md:165` concludes "another region's leader in town *N* is a datapack
   entry". A tower of N tiers x M variants is N x M generated files; nothing new is needed.
   Variety is then *pre-rolled*, not per-battle.
2. **Chosen per battle from many authored ids** — either by a function deciding which id to
   `summon_persistent`, or by the spawner block, whose `TrainerIds` is a string list and which
   "shuffles and spawns the first id that passes basic checks, with no series or `requiredDefeats`
   check, and the trainer is shared" (`docs/world-building/NAVIGATION.md:171-173`, from a jar read).
   The shuffle is the only randomiser rctmod gives us, and it is **group-wide, not per player**.
3. **Not by scaling to the player.** rctmod scales *spawn eligibility* to the player
   (`maxLevelDiff`, `forceBattleMaxLevelDiff`) and enforces a level cap, but no documented field
   rewrites a team's levels. A mob **can** impose a cap: `relativeLevelCap`, "Level cap enforced by
   this trainer relative to the strongest pokemon in the party" (docs `.../mobs/`) — useful for a
   tier that must be fought at a ceiling, and **untested by us**.

## 3. Per-player state

### VERIFIED

| Claim | Source |
| --- | --- |
| "**Every player has their own level cap**"; only trainers from a player's current series are listed in their trainer card and spawn for them | docs `gameplay/progression/` |
| rctmod keeps a **per-player defeat count per trainer id**, readable and writable by command: `rctmod player get defeats <trainerId> [<player>]` ("Retrieves the current number of defeats the given player has against the specified trainer"), `rctmod player set defeats <trainerId> [<players>] <value>` (op level 2), plus `get type_defeats`, `get progress`, `set progress (before\|after) <trainerId>`, `add progress`, `get/set series`, `get luck`, `get level_cap` | docs `gameplay/commands/` |
| That per-player count is **persistent and is the thing Cobbleverse's own loot tables gate on**: each Kanto leader guards its badge with `rctmod:defeat_count == 1`, described as "the player's saved win count" | `docs/STATE.md:172` (read from `COBBLEVERSE-RCT-DP-v20`, 2026-09-24) |
| It increments on rematches: a second win against Brock was observed at "rctmod defeats 2" | the owner on staging, 2026-09-24, `docs/STATE.md:172` |
| A **loot condition** `rctmod:defeat_count` exists with fields `count` and `comparator`, and "Compares the defeats a player has against a trainer with the specified value"; a sibling condition `rctmod:level_range` takes `range {min, max}` | docs `configuration/data_pack/loot_tables/`, with the full example table quoted there |
| An **advancement trigger** `rctmod:defeat_count` exists. Jar-read codec fields: `player`, `count`, `trainer_ids`, `trainer_type`. It fires for players on the **winning side** of a finished battle, and never on a loss, a forfeit, or a defeat set by command | `experiments/EXP-020-flag-driven-waystones/results.json:8` (codec fields from `DefeatCountTriggerInstance`); EXP-027; `tools/route_trainers.py:51-57`; `docs/STATE.md:171` |
| Per-player flags survive a server stop: `gym1_cleared` was in the saved world after a stop (EXP-027) | `docs/STATE.md:171` |
| The trainer **entity's** per-player memory does **not** persist: `TrainerMob.winsAndDefeats` is never saved | bytecode read 2026-09-24, `tools/route_trainers.py:69-70` |
| `Cooldown` is entity NBT on a shared trainer, "so it cannot be held per player" | `tools/route_trainers.py:366-367` |
| Only one trainer per identity can exist: "it is impossible for multiple trainers with the same _identity_ to spawn"; a spawner "will never spawn a trainer if another entity with the same trainer identity already exists in the world"; config `uniqueTrainerRadius = 151` narrows that to a radius | docs `gameplay/entities/`, `gameplay/blocks/`; `base-pack/cobbleverse/config/rctmod-server.toml:52-55` |

**Two stores, and the distinction is the whole answer to question 3.** The *player's* defeat count is
per player and persists; the *mob's* win/defeat memory is per entity and does not. Our rematch
observations are explained by neither being broken: the persistent-trainer branch of
`couldBattleAgainst` never consults the player's count at all.

### ASSUMED

- That `rctmod player get defeats` prints a value a function can capture with `execute store result`.
  Inferred from `rctmod player get level_cap` doing exactly that in the level-cap design
  (`docs/research/notes/level-cap-catch-block.md`, via `docs/STATE.md:173`). **Not verified for
  `get defeats`.** If true it is the cleanest per-win hook the arena could have (see EXP-A3).
- That `rctmod player set defeats … 0` is a safe way to reset a tier (it is the documented op command,
  but EXP-027 observed that a defeat *set by command* fires no advancement — so setting it does not
  re-run reward functions, which is probably what we want and is worth confirming).

### Not possible without something we do not have

A champion that is a **different entity per player**, or a tier whose occupant differs per player.
One `rctmod:trainer` is one shared entity, and the unique-identity rule actively prevents duplicates.
`docs/mechanics/GYM_INTERIORS.md:189` records the real fix as "per-player trainers through the scene
runtime", gated on the unrun EXP-034 — i.e. not available.

- That `comparator` on the `rctmod:defeat_count` loot condition takes the usual comparison operators.
  The field name is documented; **its accepted values are not quoted anywhere** — do not write one
  without checking. This matters: "pay the small purse only when defeats ≥ 2" depends on it.

| `series` | "A list of series ids that this trainer belongs to", default `[]` | docs `.../mobs/` |
| `requiredDefeats` | "A **2-dimensional** list of trainer ids of which **at least one trainer per inner list** must be defeated", default `[]` — i.e. OR within an inner list, AND across them | docs `.../mobs/` |

| `signatureItem` | "defines the item that can be used to configure a trainer spawner" | docs `.../mobs/` |
| Series JSON | `title`, `description` (translatable), `difficulty` [1-10] default 5, `initialLevelCap` [1-100], `relativeLevelCap` [-100,100], `requiredSeries` (2-D, e.g. `[["radicalred","unbound"],["bdsp"]]`), `hideTrainerIdentities` default true | docs `configuration/data_pack/series/` |
| Series is **per player** and switchable: `rctmod player set series <seriesId> [<players>] [completed <count>]`; a switch clears progress defeats and keeps `completedSeries`; the cap restarts at the series' `initialLevelCap`, else the config's | docs `gameplay/commands/`; `docs/world-building/NAVIGATION.md:151-152` (from `LevelUtils.levelCap`) |
| The level cap is **derived from the player's next required trainer** in their series plus `relativeLevelCap`; "to increase the level cap players have to defeat key trainers in a certain order"; series "can support optional and non-linear paths" | docs `gameplay/progression/`; `base-pack/cobbleverse/config/rctmod-server.toml:145-150` |
| Cobbleverse already chains Kanto this way, and our own route order is expressed by setting `requiredDefeats` in our data | `docs/world-building/NAVIGATION.md:150, 213` |
| The special series ids are `empty` and `freeroam`; `freeroam` grants a level cap of 100 and lets a player pause and resume their series; `freeroamRequiresCompletedSeries` gates it | `base-pack/cobbleverse/config/rctmod-server.toml:152-161`; docs `gameplay/progression/` |
| Our placed trainers deliberately opt out of all of it: `"type": "normal", "series": [], "requiredDefeats": [], "optional": true, "spawnWeightFactor": 0` | `tools/route_trainers.py:198-200` |

**So "beat tier N before tier N+1" is native, free and per player:** tier N+1's mob file carries
`requiredDefeats: [["arena_tier_<N>_champion"]]`, and rctmod refuses the battle with the
`missing_required_trainer_leader` dialog until the player's own saved defeat count for tier N is
nonzero. This is exactly the mechanism Cobbleverse uses to chain the Kanto leaders.

### ASSUMED / the catch

- **A tower on a series would move every climber's level cap.** The cap is computed from the player's
  next required trainer in their *current* series, and our campaign already puts players in a Kanto
  series with authored caps. Putting arena tiers into that series would make the arena dictate the
  level cap; giving the arena its own series would require a player to leave Kanto to climb.
  **Therefore the arena should use `requiredDefeats` with `series: []` and `optional: true`** — the
  gate without the cap. VERIFIED that both fields are independent in the schema; **not verified** that
  `requiredDefeats` is enforced for a trainer belonging to no series. That is the single most
  important thing to test before building the tower (EXP-A1).
- That `relativeLevelCap` on a *mob* could impose a ceiling for one tier without a series. The field is
  documented; its interaction with a seriesless trainer is unknown.

## 6. Sketch of the tower, with every piece's status

| Piece | Mechanism | Status |
| --- | --- | --- |
| A champion stands on each tier | `rctmod trainer summon_persistent <id> <x> <y> <z>` from `tools/reapply.py` (R17), or an `rctmod:trainer_spawner` with `TrainerIds` | VERIFIED, in use for 28 trainers |

| Money every fight | CobbleDollars `earnCobbleDollarsFromNPC` | VERIFIED in game, amount formula unknown |
| First-clear prize vs per-win purse | `rctmod:defeat_count` loot condition (`count`, `comparator`) in the tier's loot table | condition VERIFIED in Cobbleverse's own data and in the docs; `comparator` values unquoted |
| An exact, authored purse per tier | a function; needs a per-win trigger (poll `get defeats`, or TBCS) | **not proven** (EXP-A3) |
| "You hold tier N" per player | our quest fields via `runmolang` + `q.player.save_data()`, or a scoreboard, or an advancement flag | all three VERIFIED in this repo; the advancement fires once only |
| A champion refusing a player who already holds the tier | `data merge entity <selector> {Cooldown:N}` each cycle | VERIFIED; **shared entity, so it cannot be per player** |
| Randomised challenger teams | our generator emitting many ids + a function or the spawner's shuffle | build-time only; no runtime pool |
| Teams scaled to the climber | nothing in rctmod | **not available** |
| A different champion per player | nothing | **not available** |

Two further cautions carried from existing findings, because an arena is the shape of thing that hits
both:

1. **A refightable trainer is a level-cap bypass.** `data/level_cap.json` caps *catching*, not
   *battling*, so endless battles give endless XP (`tools/route_trainers.py:276-278`). A tower is a
   deliberate XP faucet; it has to be priced or capped on purpose, not by accident.
2. **Our list is not the world.** A champion spawned by a `trainer_spawner` inside a template is not
   in `data/placements.json` and will be missed by any cycle built from `placements()` — the exact gap
   that left eight gym leaders and the League's five with no rematch hold-off
   (`tools/route_trainers.py:264-272, 315-326`). Any arena tool must sweep or use a world-shaped
   predicate.
